## Exercise 00 — Терминология
**Что делать:** Сопоставить 4 термина (REST, Кеширование, Масштабируемость, Асинхронность) с их определениями из списка (8 вариантов). Для каждого термина выбрать правильное определение.

**Зачем:** Проверить понимание базовых понятий REST-интеграции перед началом практической работы.

## Exercise 01 — Подготовка данных
**Что делать:** Найти студентов из другой группы, которые делали проект BSA09 (база данных и словарь данных). Взять у них классы (сущности) для UC02 (формирование расписания) и UC04 (регистрация клиента менеджером). Также взять свои классы. Собрать структуры данных и описание атрибутов из двух источников.

**Зачем:** Для интеграции нужны данные из разных систем. Нужно сравнить, как одни и те же сущности описаны в разных местах (маппинг).

## Exercise 02 — Актуализация UC04
**Что делать:** Взять UC04 (регистрация клиента менеджером). Детализировать его: расписать полную последовательность шагов, альтернативные сценарии для каждого шага. Для каждого шага указать: какое приложение выполняет (сервер, клиент, сервис) и какая роль. Для шагов с интеграцией указать интеграционные методы. Выписать используемые справочники. Если справочники участвуют в интеграции — доработать UC с учётом передачи справочных данных (передать целиком, передать только нужные записи, передавать по мере необходимости).

**Зачем:** UC должен отражать не только бизнес-логику, но и технические детали интеграции, чтобы разработчики понимали, где и как происходит обмен данными.

## Exercise 03 — Интеграция справочников
**Что делать:** Для UC04 выписать все используемые справочники. Для каждого решить, нужна ли интеграция. Если нужна — выбрать вариант интеграции:
- передача полного справочника
- передача дельты (только изменений)
- передача только связанных записей
- поиск записи по передаваемым данным

В соответствии с выбранным вариантом добавить метод интеграции.

**Зачем:** Справочники могут быть в разных системах. Нужно решить, как они синхронизируются, чтобы не было расхождений.

## Exercise 04 — Определение и описание методов
**Что делать:** Для каждого случая интеграции в UC04 сформировать наборы "запрос-ответ". Определить, какой HTTP-метод (GET, POST, PUT, DELETE) подходит. Критерии выбора: какая CRUD-операция, нужна ли безопасность (метод не изменяет данные), нужна ли идемпотентность (повторный вызов даёт тот же результат). Для каждого запроса указать: метод, URL-путь, параметры, тело запроса. Для каждого ответа указать: код состояния, тело ответа (минимум 2 ответа: успех и ошибка).

**Зачем:** REST-интеграция строится на HTTP-методах. Нужно правильно выбрать метод под каждую операцию.

## Exercise 05 — Описание элементов запроса/ответа
**Что делать:** Для каждого варианта интеграции из UC04 детально описать все поля в теле запроса и ответа. В таблице указать:
- вариант интеграции, назначение, метод, направление
- для каждого поля: идентификатор, бизнес-название, тип данных, длина, обязательность, соответствие в системе-отправителе/получателе, комментарии

**Зачем:** Это спецификация API — контракт между системами. Без неё разработчики не поймут, какие поля и в каком формате передавать.

## Exercise 06 — Маппинг
**Что делать:** Для каждого варианта интеграции UC04 выполнить маппинг — сопоставить поля из системы-отправителя с полями в сообщении, и из сообщения с полями в системе-получателе. В таблице указать для стороны системы: сущность, блок, поле, тип, размерность, обязательность, условия; для стороны сообщения: соответствующие поля из Exercise 05.

**Зачем:** Данные в разных системах могут храниться по-разному. Маппинг показывает, как преобразовывать данные при передаче.

## Exercise 07 — Описание ошибок
**Что делать:** Для каждого варианта интеграции UC04 описать требования к обработке ошибок. Указать: проверяемый элемент, условие проверки, код ошибки, сообщение об ошибке, критичность. Учесть разные типы ошибок: нарушение обязательности полей, нарушение типа, нарушение размерности, логические условия, недоступность внешней системы, несоответствие ссылок на справочники. Описать не менее 15 требований к обработке ошибок.

**Зачем:** API должен корректно сообщать об ошибках, чтобы отправитель понимал, что пошло не так и как исправить.
