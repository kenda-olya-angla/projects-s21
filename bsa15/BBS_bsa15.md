## Exercise 02 — Актуализация UC04 «Зарегистрировать клиента (менеджер)»

**UC04: Зарегистрировать клиента (менеджер)**

**Контекст использования:** Менеджер, при общении с клиентом по телефону, регистрирует клиента, чтобы записать его на обслуживание.  
**Область действия:** Барбершоп, оказание услуг клиентам.  
**Уровень:** цель пользователя.  
**Основное действующее лицо:** менеджер.

**Предусловия:**  
- Клиент позвонил менеджеру.  
- Менеджер авторизован в системе.  
- Актуальная версия справочника «Каналы связи» доступна.

**Основной сценарий:**

1. Менеджер открывает страницу регистрации клиента (Веб-приложение, роль: Менеджер).  
2. Менеджер вводит номер телефона и имя, которое клиент сообщил по телефону (Веб-приложение, роль: Менеджер).  
3. Клиентское приложение отправляет данные на сервер (`POST /api/clients`, роль: Система).  
4. Сервер проверяет наличие телефона в базе (`GET /api/clients/check-phone`, роль: Сервер).  
5. Телефон не найден → система создаёт нового клиента и генерирует временный пароль (Сервер).  
6. Система отправляет СМС с данными регистрации (`POST /api/sms/send`, роль: Сервис уведомлений).  
7. Менеджер получает подтверждение об успешной регистрации (Веб-приложение, роль: Менеджер).

**Альтернативный сценарий (к шагу 4):**

4a. Введённый телефон уже зарегистрирован в системе:  
   4a.1. Сервер возвращает ошибку 409 Conflict (Сервер).  
   4a.2. Система сообщает менеджеру, что такой номер телефона уже зарегистрирован (Веб-приложение, роль: Менеджер).  
   4a.3. Менеджер предлагает клиенту назвать другой номер телефона или отказаться от регистрации (Веб-приложение / вне системы, роль: Менеджер).

**Справочники, используемые в UC:**  

| № | Название справочника     | Назначение в UC                                      | Участвует в интеграции? | Вариант передачи |
|---|--------------------------|------------------------------------------------------|-------------------------|------------------|
| 1 | Каналы связи             | Выбор предпочтительного канала уведомлений клиента   | Да                      | Полная передача справочника до выполнения UC (в предусловии) |
| 2 | Роли сотрудников         | Проверка, что текущий пользователь — менеджер       | Нет                     | Локальный справочник |

## Exercise 03 — Интеграция справочников

**1. Справочники, используемые в UC04:**

| № | Название справочника       | Назначение использования                          | Требуется интеграция? | Причина                                      | Вариант интеграции                  | Метод интеграции                  |
|---|----------------------------|---------------------------------------------------|-----------------------|----------------------------------------------|-------------------------------------|-----------------------------------|
| 1 | Каналы связи               | Выбор предпочтительного канала уведомлений        | Да                    | Могут добавляться новые каналы               | Передача полного справочника        | `GET /dicts/contact-channels`     |
| 2 | Роли сотрудников           | Проверка прав доступа менеджера                   | Нет                   | Редко обновляется, достаточно локальной копии | Локальный справочник                | —                                 |
| 3 | Источники регистрации      | Фиксация источника обращения клиента              | Да                    | Для маркетинговой аналитики                  | Поиск записи справочника            | `GET /dicts/registration-sources` |

**2. Детальное описание интеграции справочников**

**Каналы связи**

- **Назначение:** Используются для отправки уведомлений клиенту (SMS, Telegram, WhatsApp и др.).
- **Тип интеграции:** Передача полного справочника.
- **Когда вызывается:** При входе менеджера в систему, раз в день или при отсутствии локальных данных.
- **Метод:** `GET /dicts/contact-channels`

**Пример ответа:**
```json
[
  { "id": 1, "name": "SMS" },
  { "id": 2, "name": "Telegram" },
  { "id": 3, "name": "WhatsApp" },
  { "id": 4, "name": "VK" }
]
```

**Источники регистрации**

- **Назначение:** Позволяет указать, откуда клиент обратился (звонок, сайт, акция и т.д.).
- **Тип интеграции:** Поиск записи справочника по передаваемому значению.
- **Когда вызывается:** При регистрации клиента, если менеджер указывает источник.
- **Метод:** `GET /dicts/registration-sources?name=phone_call`

**Пример ответа:**
```json
{
  "id": 7,
  "name": "phone_call",
  "description": "Регистрация по телефону"
}
```

## Exercise 04 — Определение и описание методов (UC04)


### 1. Регистрация нового клиента

| Вопрос | Ответ |
|--------|-------|
| Может ли менеджер зарегистрировать нового клиента с указанными именем и телефоном? | Да, если телефон уникален и данные валидны |

**Метод:** `POST /api/clients`

**CRUD:** Create

**Идемпотентность:** Нет

**Безопасность:** Нет

**Тело запроса:**
```json
{
  "name": "Иван Петров",
  "phone": "+79991234567",
  "preferredChannel": "SMS"
}
```

**Успешный ответ (201 Created):**
```json
{
  "id": 123,
  "login": "+79991234567",
  "temporaryPassword": "f3H8lS2",
  "message": "Клиент зарегистрирован. Уведомление отправлено по SMS."
}
```

**Неуспешный ответ (409 Conflict):**
```json
{
  "error": "ClientAlreadyExists",
  "message": "Клиент с таким номером телефона уже зарегистрирован."
}
```


### 2. Проверка уникальности номера телефона

| Вопрос | Ответ |
|--------|-------|
| Свободен ли указанный номер телефона для регистрации? | Да, если номер не зарегистрирован в системе |

**Метод:** `GET /api/clients/check-phone?phone=+79991234567`

**CRUD:** Read

**Идемпотентность:** Да

**Безопасность:** Да

**Успешный ответ (200 OK):**
```json
{
  "exists": false
}
```

**Неуспешный ответ (400 Bad Request):**
```json
{
  "error": "InvalidPhoneFormat",
  "message": "Неверный формат номера телефона"
}
```


### 3. Отправка СМС-уведомления

| Вопрос | Ответ |
|--------|-------|
| Может ли система отправить SMS с указанным текстом на указанный номер? | Да, если номер валидный и сервис доступен |

**Метод:** `POST /api/sms/send`

**CRUD:** Create

**Идемпотентность:** Нет

**Безопасность:** Нет

**Тело запроса:**

{
  "phone": "+79991234567",

**Успешный ответ (200 OK):**

## Exercise 08 — Актуализация UC02 «Сформировать расписание мастера»

**UC02: Сформировать расписание мастера**

**Контекст использования:** Менеджер создает расписание работы мастера в виде слотов, доступных для записи клиентов.

**Область действия:** Барбершоп, оказание услуг клиентам.

**Уровень:** Цель пользователя.

**Основное действующее лицо:** Менеджер.

**Предусловия:**
- Менеджер получил график работы мастеров (офлайн или из другой системы).
- Менеджер авторизован в системе.
- Менеджер зашел на веб-приложение барбершопа через браузер.

---

### Основной сценарий

1. Менеджер открывает страницу ввода слотов (Веб-приложение, роль: Менеджер).

2. Менеджер выбирает дату, время (начало слота), мастера из справочника «Сотрудники», отфильтрованного по роли «Мастер» (Веб-приложение → Сервер, роль: Менеджер).  
   *Интеграционный метод:* `GET /api/employees?role=master`

3. Система проверяет, не забронирован ли выбранный слот (Сервер → Сервис слотов, роль: Система).  
   *Интеграционный метод:* `GET /api/slots/check-availability?date=...&time=...&masterId=...`

4. Менеджер подтверждает создание слота (Веб-приложение, роль: Менеджер).

5. Система закрепляет слот (дата, время, мастер) (Сервер → Сервис слотов, роль: Система).  
   *Интеграционный метод:* `POST /api/slots`

### Альтернативные сценарии

**К шагу 1: Страница ввода слотов недоступна**

1a.1. Система возвращает ошибку 503 Service Unavailable (Сервер, роль: Система).

1a.2. Менеджер повторяет попытку позже (Вне системы, роль: Менеджер).

**К шагу 2: Справочник мастеров недоступен**

2a.1. Система возвращает ошибку 503 Service Unavailable (Сервер, роль: Система).

2a.2. Менеджер повторяет попытку позже (Вне системы, роль: Менеджер).

**К шагу 3: Выбранный слот уже забронирован клиентом**

3a.1. Система сообщает, что выбранный слот уже забронирован клиентом (Сервер, роль: Система).

3a.2. Менеджер связывается с клиентом по телефону и договаривается о переносе (Вне системы, роль: Менеджер).

3a.3. Менеджер вносит новое время / мастера в систему вручную (Веб-приложение → Сервер, роль: Менеджер).

3a.4. Система обновляет слот и уведомляет клиента по СМС (Сервер → Сервис уведомлений, роль: Система).  
   *Интеграционный метод:* `POST /api/sms/send`

**К шагу 4: Менеджер отменил создание слота**

4a.1. Менеджер нажимает кнопку «Отмена» (Веб-приложение, роль: Менеджер).

4a.2. Система закрывает форму ввода слотов без сохранения данных (Сервер, роль: Система).

**К шагу 5: Ошибка при сохранении слота**

5a.1. Система возвращает ошибку 500 Internal Server Error (Сервер, роль: Система).

5a.2. Система предлагает менеджеру повторить попытку или обратиться в поддержку (Веб-приложение, роль: Система).

5a.3. Менеджер повторяет попытку создания слота (Веб-приложение, роль: Менеджер).

### Справочники, используемые в UC

| № | Название справочника | Назначение в UC | Участвует в интеграции? | Вариант передачи |
|---|----------------------|-----------------|-------------------------|------------------|
| 1 | Сотрудники (роль «Мастер») | Выбор мастера для создания слота | Да | Получение отфильтрованного списка |
| 2 | Роли сотрудников | Проверка, что сотрудник является мастером | Нет | Локальный справочник |

### Интеграционные методы

| Назначение | Метод | URL |
|------------|-------|-----|
| Получение списка мастеров | `GET` | `/api/employees?role=master` |
| Проверка доступности слота | `GET` | `/api/slots/check-availability` |
| Закрепление слота | `POST` | `/api/slots` |
| Уведомление клиента | `POST` | `/api/sms/send` |

## Exercise 09 — Определение и описание методов (UC02)

### Интеграция 1: Проверка занятости слота

| Вопрос | Ответ |
|--------|-------|
| Свободен ли указанный слот для записи клиента? | Да, если слот не забронирован |

**Вопросы-ответы:**
- CRUD-операция: **Read**
- Метод должен быть безопасным? — **Да**
- Требуется идемпотентность? — **Да**
- Подходит метод: **GET**

**Метод:** `GET /api/slots/check-availability`

**Параметры запроса (query string):**
- `date` — дата слота (формат YYYY-MM-DD)
- `time` — время начала (формат HH:mm)
- `masterId` — идентификатор мастера

**Пример запроса:**
```
GET /api/slots/check-availability?date=2025-07-15&time=10:00&masterId=123
```

**Успешный ответ (200 OK):**
```json
{
  "available": true
}
```

**Неуспешный ответ (400 Bad Request):**
```json
{
  "error": "InvalidParameters",
  "message": "Missing or invalid date, time, or masterId"
}
```

### Интеграция 2: Создание слота

| Вопрос | Ответ |
|--------|-------|
| Может ли менеджер создать новый слот для мастера? | Да, если слот свободен и данные валидны |

**Вопросы-ответы:**
- CRUD-операция: **Create**
- Метод должен быть безопасным? — **Нет**
- Требуется идемпотентность? — **Нет**
- Подходит метод: **POST**

**Метод:** `POST /api/slots`  *(исправлено: было /api/schedule)*

**Тело запроса:**
```json
{
  "date": "2025-07-15",
  "startTime": "10:00",
  "masterId": 123
}
```

**Успешный ответ (201 Created):**
```json
{
  "message": "Slot successfully created",
  "slotId": 12345
}
```

**Неуспешный ответ (409 Conflict):**
```json
{
  "error": "SlotOccupied",
  "message": "Selected slot is already occupied by a client"
}
```
