## Exercise 00 — Выделение потоков данных
**Что делать:** Для задачи 2 (доставка заказов) найти в тексте не менее 6 потоков данных — то, что передаётся между системами. Для каждого потока указать: название, назначение (зачем передаём), направление (в нашу систему или из неё).

**Примеры из задачи:** заказы от магазинов поступают в систему, информация о доставке уходит в бухгалтерию, начисленная оплата приходит из бухгалтерии, база адресов загружается разово.

**Зачем:** Понять, какие данные и куда движутся. Интеграция начинается с выявления потребности в обмене данными.

## Exercise 01 — Определение мастер-систем (для входящих данных)
**Что делать:** Взять каждый входящий поток данных. Определить, какие внешние системы в окружении теоретически могут быть источником этих данных. Выбрать одну мастер-систему (главный источник) для каждого потока. Кратко обосновать выбор: зачем именно эта система передаёт данные.

**Пример:** Заказы от магазинов — мастер-системой может быть CRM магазина или сам магазин передаёт данные через оператора.

**Зачем:** Для каждого входящего потока нужно определить, кто является авторитетным источником (мастером). Это важно для устранения конфликтов данных.

## Exercise 02 — Определение систем-получателей (для исходящих данных)
**Что делать:** Взять каждый исходящий поток данных. Определить, какие системы могут быть заинтересованы в получении этих данных. Выбрать систему-получателя. Обосновать выбор. Проверить, нет ли противоречий между мастер-системой и системой-получателем для связанных данных (чтобы не было циклической зависимости).

**Пример:** Информация о доставке → бухгалтерская система. Начисленная оплата ← бухгалтерская система.

**Зачем:** Понять, кому нужны данные из нашей системы. Убедиться, что нет конфликтов (например, две системы не пытаются быть мастером для одних и тех же данных).

## Exercise 03 — Словарь данных для потоков
**Что делать:** Для каждого потока данных разработать словарь данных — спецификацию того, что именно передаётся. Указать: название потока, назначение, направление. Описать структуру: блоки данных, вложенность, обязательность блоков. Для каждого атрибута (поля) указать: название, тип данных, длину (для текста), обязательность, ограничения.

**Пример:** Поток "Заказ" содержит блоки: заголовок (номер, дата), состав (товары), адреса (место комплектации, место доставки). У каждого поля — тип и правила.

**Зачем:** Чтобы разработчики знали, какие данные и в каком формате передавать. Это основа для маппинга (преобразования между системами).

## Exercise 04 — Сценарии интеграции
**Что делать:** Для каждого потока данных описать сценарий интеграции в виде UC (варианта использования) или нарисовать диаграмму. Показать: какая система инициирует передачу, что происходит, как обрабатываются ошибки.

**Зачем:** Сценарий показывает, как именно и при каких условиях происходит обмен данными. Это помогает согласовать поведение систем.

## Exercise 05 — Требования к объёму и количеству данных
**Что делать:** Для каждого потока данных определить количественные характеристики:
- среднее количество сообщений в единицу времени (в день/час/минуту)
- средний размер одного сообщения
- периоды пиковой нагрузки (когда больше всего данных)
- пиковое количество сообщений в единицу времени

**Пример:** В будни — 100 заказов в час, размер 2 КБ. В пятницу вечером пик — 500 заказов в час.

**Зачем:** Это критерии для выбора стиля интеграции и для настройки производительности. Если пик 500 сообщений в минуту — не подойдёт обмен файлами раз в час.

## Exercise 06 — Частота и сроки доставки
**Что делать:** Для каждого потока данных определить временные характеристики:
- желаемая частота передачи (как часто нужно отправлять)
- желаемые сроки доставки (максимальное время от отправки до получения)
- минимально и максимально возможная частота (допустимый диапазон)
- минимально и максимально возможные сроки доставки

**Пример:** Для оплаты по карте — частота реального времени, срок доставки 1-2 секунды. Для ежемесячных отчётов — раз в месяц, срок доставки — до 10 числа.

**Зачем:** Это ещё один критерий выбора стиля интеграции. Синхронный RPC подходит для быстрых ответов, а обмен файлами — для больших, не срочных отчётов.
