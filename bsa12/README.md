## Exercise 00 — Определение нефункциональных требований
**Что делать:** Изучить список из 9 предложений (смесь функциональных и нефункциональных требований). Выписать номера только тех предложений, которые содержат нефункциональные требования (как система работает — скорость, доступность, сохранность данных).

**Пример:** "Система формирует список свободных слотов" — функциональное. "Формирует список за 10 секунд при 1000 пользователях" — нефункциональное.

**Зачем:** Научиться отличать функциональные требования (что делает) от нефункциональных (как делает).

## Exercise 01 — Классификация нефункциональных требований
**Что делать:** Взять 11 нефункциональных требований и для каждого указать тип из предложенного списка: доступность, надежность, масштабируемость, локализация, удобство использования, производительность, совместимость, долговечность, безопасность.

**Пример:** "Восстановление после сбоя за 30 минут" → надёжность. "Доступность 99% времени" → доступность.

**Зачем:** Систематизировать НФТ по категориям, чтобы понимать, с какими атрибутами качества мы работаем.

## Exercise 02 — Выбор НФТ для задач
**Что делать:** Для задачи 1 (барбершоп) и задачи 2 (доставка) выбрать не менее 7 типов НФТ из списка (производительность, безопасность, масштабируемость и т.д.). Для каждого типа указать приоритет от 1 (самый важный) до 5 (наименее важный). Приоритеты могут различаться для двух задач.

**Пример:** Для доставки скорость (производительность) может быть приоритетом 1, а локализация — 5. Для барбершопа наоборот.

**Зачем:** НФТ бывают разные, и не все одинаково важны. Нужно определить, на чём делать акцент в каждой системе.

## Exercise 03 — Атрибуты производительности
**Что делать:** Для каждой задачи выделить 3 важных сценария с точки зрения бизнеса и клиентов. Для каждого сценария указать: роли участников, примерное количество зарегистрированных пользователей, одновременно работающих (обычно и в пик). Затем выбрать 3–5 операций/страниц, у которых нужно контролировать скорость отклика, и указать допустимое время.

**Пример:** "Просмотр свободных слотов клиентом: при 1000 одновременных пользователей — не более 3 секунд".

**Зачем:** Производительность нужно измерять в цифрах, а не "быстро". Без этих цифр разработчики не знают, к чему стремиться, а тестировщики — как проверять.

## Exercise 04 — Атрибуты доступности и надёжности
**Что делать:** Для каждой задачи описать требования к доступности (когда система должна работать, какой процент времени, допустимые перерывы) и к надёжности (восстановление после сбоев, сохранность данных, допустимые потери).

**Пример:** "Система доступна с 9:00 до 21:00 99% времени. При сбое восстановление не более 30 минут, потеря данных не более чем за 5 минут до сбоя".

**Зачем:** Пользователи и бизнес зависят от системы. Нужно чётко понять, сколько простоев допустимо и как быстро система должна "оживать" после сбоя.

## Exercise 05 — Атрибуты масштабирования и локализации
**Что делать:** Для каждой задачи определить, нужна ли масштабируемость (способность расти — больше точек, больше пользователей, больше регионов). Если да — описать требования. Определить, нужна ли локализация (учёт региональных особенностей: язык, часовые пояса, валюта). Если да — описать.

**Пример для задачи 1:** Масштабирование нужно — сначала 5% точек и 75 мастеров, потом вся сеть по всем регионам РФ. Локализация нужна — региональное время.

**Зачем:** Система может расти. Нужно заранее предусмотреть, как она будет расширяться без переписывания "с нуля".

## Exercise 06 — Атрибуты безопасности (пароли и логирование)
**Что делать:** Для каждой задачи описать требования по безопасности. Для задачи 1 и задачи 2 использовать РАЗНЫЕ подходы (например, в одной строгие пароли, в другой — проще). Описать:
- требования к составу пароля (длина, символы)
- правила смены/восстановления пароля
- нужна ли двухфакторная аутентификация, для каких действий, как работает
- что нужно логировать (какие операции, какие данные, какие служебные поля: дата, время, пользователь)

**Зачем:** Безопасность — не "чтобы было". Нужны конкретные, измеримые требования. Разные системы требуют разного уровня защиты.
