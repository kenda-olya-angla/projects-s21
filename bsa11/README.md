## Exercise 00 — Выбор формы представления продукта
**Что делать:** Для задачи про барбершоп определить и записать в таблицу:
- на каких устройствах будет использоваться система (компьютер, телефон, планшет)
- тип приложения (корпоративная система, маркетплейс и т.д.)
- способы управления (мышь, клавиатура, сенсор, голос)
- потребности локализации (язык, часовые пояса, региональные особенности)

**Зачем:** Дизайнер должен понимать, для каких устройств и условий он рисует интерфейс. Мобильное приложение и десктопная версия — это очень разные подходы.

## Exercise 01 — Экранные формы справочников и классификаторов
**Что делать:** Составить список всех справочников (Клиенты, Сотрудники, Услуги, Роли сотрудника, Услуги мастера). Для каждого нарисовать эскиз экранной формы (список записей + операции). Описать основные операции (создание, чтение, редактирование, удаление): кто может, при каких условиях, какие последствия. Описать обеспечивающие операции: сортировка (по каким полям), фильтрация (по каким полям, сохранять ли фильтры), поиск (по каким полям, точность совпадения). Указать, что логировать.

**Зачем:** Справочники — основа системы. Их интерфейсы должны быть удобными и понятными, а права доступа — чёткими.

## Exercise 02 — Данные на экранных формах справочников
**Что делать:** Для каждого справочника детально описать поля на экранной форме списка: название поля, формат (тип данных, длина), обязательность, значение по умолчанию, как отображать пустые значения, что делать, если текст не влезает. Описать пагинацию (нужна ли), расчёт сумм/количества записей, проверки и сообщения об ошибках.

**Зачем:** Это спецификация для разработчиков и дизайнеров. Без неё нельзя понять, какие поля и в каком формате выводить на экран.

## Exercise 03 — Ключевые сценарии ролей
**Что делать:** Для каждой роли (менеджер, мастер, клиент) разработать ключевые сценарии — как они решают свои главные задачи с помощью системы. Нарисовать схему задач в виде прямоугольников (экранных форм), стрелками показать переходы между ними. Для каждого перехода указать условие (действие). Предусмотреть выход до окончания процесса без сохранения.

**Зачем:** Понять, какие экраны нужны и как пользователь перемещается между ними для достижения цели. Это основа для проектирования навигации.

## Exercise 04 — Список экранных форм
**Что делать:** Составить единый список всех экранных форм для всех ролей. Для каждой формы указать: идентификатор, основное назначение (главное действие), другие возможные действия, какие данные нужны, и кто имеет право доступа к этому экрану.

**Зачем:** Не потерять ни один экран. Понять, какие экраны для каких ролей доступны и зачем они нужны.

## Exercise 05 — Экранные формы (wireframe)
**Что делать:** Для каждой экранной формы из Exercise 04 нарисовать макет (wireframe — чёрно-белый эскиз без дизайна). На макете указать: название формы, фреймы (список, карточка, операции), вызовы операций, кнопки перехода и отмены. Описать основные операции (кто может, условия, результат), обеспечивающие операции (сортировка, фильтрация, поиск), данные (объект/класс, пагинация, поля и их формат). Указать, что логировать.

**Зачем:** Wireframe — это "скелет" интерфейса. Он показывает структуру и функциональность без отвлечения на цвета и шрифты. Это то, что аналитик передаёт дизайнеру и разработчику.

## Exercise 06 — Описание контролей
**Что делать:** Для каждого экрана, где есть ввод или редактирование данных, описать контроли (проверки, валидацию). Для каждого поля указать: что проверяется, какое сообщение об ошибке, что происходит при ошибке (можно ли сохранить, блокируется ли поле, откатывается ли операция), что происходит при успешной проверке. Указать, нужно ли логировать негативные сценарии.

**Зачем:** Разработчик должен знать, как проверять вводимые данные и что делать пользователю в случае ошибки. Это критично для качества системы.
