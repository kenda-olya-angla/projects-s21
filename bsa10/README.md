## Exercise 00 — Выделение объектов со статусной моделью
**Что делать:** Для задачи про барбершоп найти сущности, которые меняют свои состояния в процессе работы системы. Например, запись может быть "новая", "подтверждённая", "выполненная". Обосновать, почему для каждой выбранной сущности нужно отслеживать жизненный цикл. Добавить в каждую сущность атрибут «Статус».

**Зачем:** Не все объекты живут статично — некоторые проходят этапы. Отслеживание статусов помогает контролировать процесс и правильно реагировать на события.

## Exercise 01 — Жизненный цикл «Слотов обслуживания»
**Что делать:** Разработать статусную модель для «Слотов обслуживания». Определить состояния от создания до выполнения услуги. Предусмотреть отказ со стороны клиента и отказ со стороны барбершопа. Проверить, есть ли эти сценарии в UC, при необходимости доработать UC. Нарисовать диаграмму состояний: состояния, переходы, исполнители, действия и условия.

**Зачем:** Слоты — центральная сущность. Их жизненный цикл должен быть чётко описан, чтобы разработчики понимали, когда и что происходит с записью клиента.

## Exercise 02 — Статусные модели других сущностей
**Что делать:** Для остальных сущностей из Exercise 00 (кроме слотов) разработать статусные модели в табличном виде. Для каждого статуса указать: исходное состояние, кто инициатор, какие действия выполняются, условия, в какое состояние переходит. Отметить начало и конец жизнен цикла.

**Зачем:** Табличный формат для менее сложных объектов удобнее диаграммы. Важно не упустить ни один этап изменения состояния.

## Exercise 03 — Действия над справочниками
**Что делать:** Для пяти справочников (Клиенты, Сотрудники, Роли сотрудника, Услуги, Услуги мастера) описать функциональность: кто создаёт, читает, редактирует, удаляет. Для каждой операции указать: условия выполнения, возможность отката, нужно ли подтверждение, какие изменения это порождает в других частях системы, нужно ли логирование, кого и как извещать.

**Зачем:** Справочники — основа системы. Их наполнением и поддержкой занимаются разные роли, нужно чётко определить права и последствия действий.

## Exercise 04 — Действия CRUD над «Слотами обслуживания»
**Что делать:** Определить для слотов, кто из ролей (менеджер, мастер, клиент, администратор) может выполнять операции создания, чтения, редактирования, удаления. Проверить, что эти операции описаны в UC. Если нет — дополнить UC и выделить изменения цветом.

**Зачем:** Слоты могут создавать менеджеры (расписание), читать — клиенты и мастера, редактировать — менеджер (перенос), удалять — возможно никто, кроме админа. Нужно явно указать, кто что может.

## Exercise 05 — Детализация операций над «Слотами»
**Что делать:** Расширить таблицу CRUD для слотов. Добавить информацию о:
- форме визуализации (список или карточка)
- подтверждении операции (нужно ли подтверждать)
- возможности отката
- сортировке и фильтрации (какие поля)
- поиске
- логировании (что записывать)
- отправке сообщений (кому и когда)

**Зачем:** CRUD — это только "что можно сделать". Разработчикам нужно больше деталей: как это должно выглядеть, какие проверки, какие побочные эффекты.

## Exercise 06 — Права доступа ролей
**Что делать:** Составить матрицу прав доступа для 6 объектов и 4 ролей (менеджер, мастер, клиент, администратор). Для каждой пары "роль — объект — операция" указать: можно или нельзя (и при каких условиях). Для разрешённых операций указать: какие изменения в других частях системы, требуется ли извещение и логирование. Отдельно: удаление только для администратора и только для устаревших записей (например, через год неактивности).

**Зачем:** Это финальный документ, который разработчики и тестировщики используют для реализации контроля доступа. Здесь не должно быть неоднозначностей.
