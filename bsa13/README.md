## Exercise 00 — Выделение типов требований и настройка системы управления
**Что делать:** В команде определить 4 типа требований (бизнес-требования, требования пользователей, функциональные, нефункциональные). Каждому типу назначить трёхбуквенный идентификатор (например, BIZ, USR, FUN, NFR). Для всех типов определить атрибуты: статус, приоритет, даты, версию, исполнителя, автора, источник, связи. Определить 8 статусов требований (Новое, На анализе, В разработке, На тестировании, Включено в патч, Отклонено, Отложено, Завершено). Развернуть личный экземпляр в системе управления задачами (Weeeek, Jira или Trello). Создать там все перечисленные требования в соответствии с определёнными атрибутами и статусами.

**Зачем:** Требования нужно не только написать, но и управлять ими — отслеживать состояние, приоритет, кто работает, откуда взялось. Система управления задачами централизует это.

## Exercise 01 — Создание требований для напоминаний
**Что делать:** Взять выделенное в задаче предложение про автоматическую отправку напоминаний. Декомпозировать его на 4 части (информирование менеджером, получение клиентом, каналы связи, настройка расписания). Для каждой части создать User Story (требования заинтересованных сторон). Затем создать функциональные требования (как система должна работать: настройка расписания, автоматическая отправка) и требования к интерфейсам (как выглядят экраны настройки). Всё зарегистрировать в системе управления задачами. Указать приоритеты, зависимости (источник — какое вышестоящее требование породило), горизонтальные связи между требованиями.

**Зачем:** Одно большое предложение в задаче — это не требование. Его нужно разбить на мелкие, связанные между собой требования разных типов, чтобы их можно было назначать разработчикам и тестировщикам.

## Exercise 02 — Создание позитивного тест-кейса для UC02
**Что делать:** Для UC02 (сформировать расписание мастера) разработать позитивные тест-кейсы — сценарии, где всё идёт по правильному пути, без ошибок. Для каждого тест-кейса указать: идентификатор, название, приоритет, предусловие, шаги выполнения (конкретные действия с корректными данными), ожидаемый результат, постусловия (как вернуть систему в исходное состояние). Поле "фактический результат" пока оставить пустым. Тест-кейс должен быть повторяемым и атомарным (независимым от других). Разместить в облачном хранилище, зарегистрировать задачу на тестирование в Weeek с ссылкой.

**Зачем:** Позитивные тест-кейсы проверяют, что система работает правильно при корректных действиях пользователя. Это основа тестирования.

## Exercise 03 — Создание негативного тест-кейса для UC02
**Что делать:** Для UC02 разработать негативные тест-кейсы — сценарии, где что-то идёт не так (некорректные данные, конфликтные ситуации, нарушение логики). Формат такой же, как в Exercise 02: идентификатор, название, приоритет, предусловие, шаги выполнения (с некорректными данными или нештатными действиями), ожидаемый результат (система должна выдать ошибку или отказать), постусловия. Поле "фактический результат" пустое. Разместить в облачном хранилище, зарегистрировать задачу в Weeek.

**Зачем:** Негативные тест-кейсы проверяют, что система корректно обрабатывает ошибки и нештатные ситуации, а не падает и не делает непонятно что.

## Exercise 04 — Оценка результата и отчёт о дефекте
**Что делать:** Выполнить позитивные тест-кейсы из Exercise 02 (мысленно или на практике с тестовым стендом). В зависимости от результатов:
- Если фактический результат совпадает с ожидаемым — отметить "успешно".
- Если не совпадает — зарегистрировать дефект (ошибку). В отчёте о дефекте указать: идентификатор, краткое описание (что, где, когда), шаги воспроизведения, ожидаемый результат, фактический результат (подчеркнуть отличие), постусловия, окружение (ОС, браузер), приоритет, важность, описание, скриншоты. В поле "фактический результат" тест-кейса поставить отметку об отрицательном результате и ссылку на дефект.

**Конкретные проверки из задания:**
1. Система говорит, что слот забронен, а клиент отрицает → расхождение.
2. Слот не забронен, система работает нормально.
3. При успешном создании слота он исчезает из свободных.
4. При неуспешном — слот остаётся свободным.

**Зачем:** Тест-кейсы выявили расхождение между ожидаемым и реальным поведением. Дефект нужно зарегистрировать, чтобы разработчик исправил, а тестировщик перепроверил.
